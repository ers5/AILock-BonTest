# 프로젝트 소개
잠긴 앱을 열려면 AI를 설득해야 하는 과사용 방지 서비스의 백엔드입니다.
사용자는 AI와 대화하며, AI는 대화 내용을 바탕으로 여러가지 요소를 고려하여 사용자에게 쓰게해줄지/말지 여부를 결정합니다.

# 담당역할
3인 팀 프로젝트에서 백엔드를 단독으로 설계·구현·배포했습니다.
대화형 판단 파이프라인, 세션 사용권 상태 모델링, 동시성 제어, PostgreSQL 및 pgvector 기반 검색, 서버 배포를 설계하고 구현했습니다.

# 사용한 기술

- **Java / Spring Boot / Spring Data JPA** — 백엔드 애플리케이션과 트랜잭션 처리
- **PostgreSQL / pgvector** — 상태 데이터 저장 및 임베딩 유사도 검색 
- **OpenAI API / Spring AI** — 사용자 입력 평가와 응답 생성 
- **OpenAI Java SDK** — logprobs가 필요한 라우터 직접 구현 

# 핵심 설계

### 동시성 처리
- 문제: LLM 판단 중 같은 세션의 요청이 겹치면, 두 요청이 동일한 turn_count와 대화 상태를 기준으로 판단하거나 같은 turn_index로 저장을 시도할 수 있습니다.
- 해결: 읽은 시점의 turn_count를 기대값으로 들고 있다가, 쓰기 시점에 현재 값이 기대값과 같을 때만 증가시키는 CAS로 처리했습니다. 동일한 값을 읽은 요청이 동시에 저장되면 하나만 성공하고, 나머지는 충돌 예외로 롤백해 중복 저장을 막았습니다.
- 검증: 194개 세션·6,649개 턴 전수 검증에서 turn_count 불일치, turn_index 중복·누락이 0건이었습니다.
### SMALL_TALK와 사용 요청의 모호성 처리
- 요구: 초기엔 SMALL_TALK를 두었다가 UNLOCK_REQUEST와 자꾸 헷갈려 제거했는데, 이후 SMALL_TALK를 다시 살려달라는 요구가 있었습니다.
- 문제: 두 의도는 표현이 겹치므로 `SMALL_TALK`를 단순히 복원하면 기존 오분류도 함께 재발할것으로 생각했습니다.
- 해결: 라우터가 출력한 상위 두 intent 후보의 `logprob` 차이인 margin을 계산했습니다. margin이 작으면 상대적 확신도가 낮다고 보고 분류를 강행하지 않고 `CLARIFY`로 전환해 사용자에게 의도를 되묻도록 했습니다. 
### 변하는 요구사항을 최소 변경으로 흡수

프로젝트 진행 중 요구사항이 자주 바뀌었고, 기존 구조를 갈아엎기보다 최소한의 변경으로 흡수하는 방향을 택했습니다.
#### 1. 세션 수명 연장

- **요구**: 기존에는 대화 세션이 최대 하루까지만 유지됐으나, 잠금 기간(약 3주) 내내 하나의 세션을 유지해달라는 요구가 생겼습니다.
- **문제**: 3주치 대화를 매 요청마다 전달하면 입력 토큰·비용·지연이 계속 증가하며, 오래된 대화가 현재 판단에 불필요하게 개입할 수 있습니다.
- **해결**: 세션과 전체 기록은 유지하되, LLM 판단에 넣는 대화만 매일 오전 6시 기준으로 잘라 최근 것만 전달하였습니다.
#### 2. 강경 거절 정책 토글화

- **요구**: 기존에는 사용자가 욕설 등 공격적인 표현을 하면, 일정 시간 동안 자동으로 거절하는 분기(hard_reject)가 있었는데, 이게 굳이 필요한가라는 요구가 있었습니다.
- **문제**: 관련 로직을 코드에서 걷어낼 시, 나중에 다시 필요해질 때 되돌리기 어렵다는 문제가 있습니다. 
- **해결**: 로직은 그대로 두고 on/off 플래그를 두어, off일 때는 욕설이 감지돼도 일반 판단 분기로 처리하도록 했습니다.
#### 3. 짧은 요청은 관대하게

- **요구**: "5분만 잠깐 쓸게" 와 같은 짧은 요청은 좀 더 쉽게 허용해달라는 요구가 있었습니다.
- **문제**: 사용자가 시간을 자연어로 제각각 표현하기 때문에, 짧은 요청을 어떻게 판정할지가 관건이었습니다. 
- **해결**: 자연어에 대한 해석은 LLM에게 맡겨야 하지만, 이 같은 과정을 위해 LLM을 호출하는건 너무 큰 비용이라고 생각했습니다. 따라서 입력에서 "N분" 을 정규식으로 파싱하고 이 N이 여러 개 일 시, 가장 큰 값을 기준으로 삼아 5분 이하일때 허용 기준점을 낮췄습니다. 
#### 4. 관리자 전용 세션 종료

- **요구**: 사용자가 예외적으로, 앱을 반드시 사용하는 상황이 올 수 있으므로 특정 세션을 삭제할 수단이 필요했습니다.
- **문제**: 폰에서 서버로 요청을 보낼 수는 있지만, 서버가 폰으로 직접 요청을 보내기는 어렵습니다. 스마트폰은 네트워크에 따라 IP가 바뀌고 외부에서 접근할 수 있는 고정된 주소도 없기 때문입니다.
- **해결**: 세션 생성 시 임의의 4자리 코드를 발급하고 참가자가 그 코드를 채팅창에 입력하면 서버가 세션과 permit을 종료합니다. 서버는 폰을 부를 필요가 사라지고 기존 채팅 경로를 그대로 재사용해 별도 통신 수단을 추가하지 않았습니다.
